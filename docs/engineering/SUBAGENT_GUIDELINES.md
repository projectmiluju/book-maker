# Book Maker Subagent Guidelines

## 1. 목적

이 문서는 `안녕, 나의 바다` 프로젝트에서 서브에이전트를 언제, 어떻게 사용할지 정의한다.

목표는 다음과 같다.

- 병렬 작업이 프로젝트 방향을 흐리지 않게 한다
- 서브에이전트 사용이 실제 생산성 향상으로 이어지게 한다
- 파일 충돌과 중복 작업을 줄인다
- 최종 통합 책임이 어디에 있는지 명확히 한다

## 2. 기본 원칙

- 서브에이전트는 기본 도구가 아니라 선택적 도구다
- 병렬화가 실제 이득일 때만 사용한다
- 이 프로젝트에서는 메인 에이전트가 필요하다고 판단하면 사용자의 추가 지시 없이 자율적으로 서브에이전트를 사용할 수 있다
- 메인 에이전트가 항상 계획, 분배, 통합 책임을 가진다
- 서브에이전트끼리 직접 협업한다고 가정하지 않는다
- write scope가 겹치는 작업에는 신중하게 접근한다

즉:

- 스킬은 반복 가능한 절차를 다루고
- 서브에이전트는 병렬 가능한 작업을 다룬다

## 3. 언제 사용해도 좋은가

아래 조건이 맞으면 서브에이전트 사용을 우선 고려할 수 있다.

- 서로 다른 파일/모듈을 독립적으로 다룰 수 있다
- 메인 에이전트가 기다리는 동안 다른 작업을 진행할 수 있다
- 탐색, 문서, 테스트, 구현 중 일부를 병렬로 분리할 수 있다
- 각 작업의 입력과 출력이 명확하다

이 프로젝트에서 좋은 예:

- 백엔드 구현과 프론트 영향 범위 탐색을 병렬로 진행
- 기능 구현과 테스트 케이스 설계를 병렬로 진행
- 코드 수정과 문서 반영 정리를 병렬로 진행
- 특정 모듈 구조 질문을 explorer 성격 작업으로 위임

## 4. 사용하면 안 좋은가

아래 상황에서는 메인 에이전트가 직접 처리하는 것이 낫다.

- 바로 다음 결정을 막는 핵심 설계 작업
- 범위가 아직 모호한 작업
- 같은 파일을 동시에 수정해야 하는 작업
- 매우 작은 수정 하나로 끝나는 작업
- 결과를 서로 기다리는 연쇄 의존 작업

이 프로젝트에서 피해야 할 예:

- 같은 인증 모듈 파일을 둘 이상의 서브에이전트가 동시에 수정
- 설계가 안 정해진 상태에서 각자 다른 방향으로 구현 시작
- 동일한 화면과 동일한 문서를 동시에 여러 에이전트가 만지는 상황

## 5. 역할 분리 기준

서브에이전트는 보통 아래 두 종류로 나눈다.

### explorer

탐색, 영향 범위 파악, 코드베이스 질문, 구조 분석에 적합하다.

좋은 예:

- auth 관련 진입점 찾기
- draft reorder와 연결된 파일 찾기
- 현재 테스트 공백 영역 정리

### worker

독립적인 코드 수정, 테스트 추가, 문서 수정에 적합하다.

좋은 예:

- `apps/api/auth/*`만 수정하는 구현 작업
- `docs/engineering/*`만 수정하는 문서 동기화
- 특정 테스트 파일만 추가하는 작업

## 6. write scope 규칙

서브에이전트를 사용할 때 가장 중요한 것은 write scope 분리다.

원칙:

- 한 서브에이전트는 가능한 한 명확한 파일/모듈 범위를 가진다
- 같은 파일을 둘 이상의 서브에이전트에게 맡기지 않는다
- 코드와 문서를 병렬로 나눌 때도 책임 파일을 구분한다

좋은 예:

- Worker A: `apps/api/src/auth/**`
- Worker B: `apps/web/app/pages/app/**`
- Worker C: `docs/engineering/**`

좋지 않은 예:

- Worker A와 B가 모두 `apps/api/src/auth/auth.service.ts` 수정
- 여러 에이전트가 동시에 `AGENTS.md`를 수정

## 7. 메인 에이전트 책임

메인 에이전트는 아래 책임을 가진다.

- 작업을 먼저 구조화한다
- 무엇을 직접 할지 먼저 결정한다
- 서브에이전트마다 목표와 범위를 분리한다
- 필요한 참고 문서를 명시한다
- 서브에이전트를 사용할 경우 사용자에게 병렬 작업 여부와 역할 분리를 알린다
- 결과를 검토하고 통합한다
- 서로 어긋난 결과를 정리한다

즉, 메인 에이전트는 단순 전달자가 아니라 리드 역할을 수행한다.

## 8. 서브에이전트 지시문 원칙

지시문에는 최소 아래가 포함되어야 한다.

- 작업 목표
- 책임 범위
- 수정 가능한 파일 또는 모듈
- 건드리면 안 되는 것
- 참고 문서
- 최종 결과에 포함할 내용

좋은 지시 예:

- `apps/api/src/auth/**` 범위에서 JWT 인증 기초 구현
- 다른 작업자가 있을 수 있으므로 타인의 변경을 되돌리지 말 것
- 수정 파일 목록과 검증 결과를 함께 보고할 것

## 9. 이 프로젝트에서 추천 패턴

### 패턴 1. 구현 + 탐색

- 메인: 핵심 기능 구현
- explorer: 영향 범위, 관련 파일, 기존 패턴 조사

### 패턴 2. 구현 + 테스트

- 메인: 기능 구현
- worker: 테스트 케이스 추가

### 패턴 3. 구현 + 문서 동기화

- 메인: 코드 수정
- worker: 문서, WORKLOG, API 계획 동기화

### 패턴 4. 프론트 / 백엔드 분리

- 메인: 백엔드 핵심 흐름
- worker: 프론트 연결 준비 또는 영향 범위 파악

## 10. 판단 질문

서브에이전트를 쓰기 전에 아래를 본다.

1. 이 작업은 메인 흐름을 직접 막는가?
2. 내가 기다리는 동안 다른 유의미한 작업을 할 수 있는가?
3. 파일 충돌 없이 책임 범위를 분리할 수 있는가?

세 질문 중 두 개 이상이 `예`라면 서브에이전트 사용 가치가 높다.

## 11. 하지 말아야 할 것

- 명확한 분리 없이 무조건 병렬화
- 설계가 안 된 상태에서 구현 작업을 여러 갈래로 시작
- 같은 파일을 여러 에이전트에 중복 할당
- 검토 없이 서브에이전트 결과를 그대로 병합
- 작은 단일 작업에도 과도하게 서브에이전트 사용

## 12. 최종 기준

좋은 서브에이전트 사용은 다음을 만족해야 한다.

- 병렬화가 실제 시간을 줄인다
- 작업 결과가 서로 충돌하지 않는다
- 메인 에이전트가 통합 비용을 감당할 수 있다
- 프로젝트 방향과 문서 기준이 흔들리지 않는다
