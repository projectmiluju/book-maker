# Book Maker Test Strategy

## 1. 목적

이 문서는 Book Maker 프로젝트의 테스트 전략을 정의한다.

목표는 단순히 테스트 코드를 "작성하는 것"이 아니라, 아래를 증명하는 것이다.

- 핵심 사용자 흐름이 안정적으로 동작한다
- 인증과 데이터 소유권이 안전하게 보호된다
- 자동 저장 같은 신뢰 민감 기능이 깨지지 않는다
- 변경이 생겨도 회귀 버그를 빠르게 발견할 수 있다
- 이 프로젝트가 포트폴리오 관점에서도 "품질을 설계한 프로젝트"로 설명될 수 있다

## 2. 테스트 철학

Book Maker는 모든 것을 E2E로만 검증하지 않는다.

또한 모든 함수를 단위 테스트로만 쪼개지도 않는다.

전략은 다음과 같다.

1. 도메인 규칙은 단위 테스트로 빠르게 검증
2. API 계약과 권한은 통합 테스트로 검증
3. 핵심 사용자 흐름은 E2E 테스트로 검증
4. 테스트 수보다 `핵심 위험 구간` 커버리지를 우선

### TDD 적용 원칙

이 프로젝트는 전체 기능을 기계적으로 TDD로 개발하지 않는다.

대신 아래 조건에 해당하는 영역에는 `Red -> Green -> Refactor` 흐름을 우선 적용한다.

- 권한 누수 위험이 있는 로직
- 데이터 무결성이 중요한 로직
- 회귀 시 사용자 신뢰를 크게 해치는 로직
- 순수 함수 또는 서비스 레벨에서 규칙 검증이 명확한 로직

즉, Book Maker의 TDD는 `전면 적용`이 아니라 `핵심 리스크 구간에 대한 선택적 TDD`를 원칙으로 한다.

## 3. 이 프로젝트에서 반드시 보호해야 할 핵심 리스크

테스트는 기능 목록이 아니라 리스크 기준으로 설계한다.

### 리스크 1. 글 유실

사용자가 입력한 기록이 자동 저장되지 않거나, 저장 실패를 인지하지 못하는 상황

### 리스크 2. 권한 누수

다른 사용자의 기록이나 초안을 ID만으로 조회/수정하는 상황

### 리스크 3. 초안 순서 무결성 붕괴

초안에 포함된 기록 순서가 꼬이거나 중복/누락이 생기는 상황

### 리스크 4. 인증 세션 단절

토큰 만료 이후 refresh가 실패하거나, 프론트에서 무한 재시도를 하는 상황

### 리스크 5. MVP 핵심 루프 회귀

기록 작성 -> 아카이브 -> 초안 생성 -> 미리보기 흐름이 변경 중 깨지는 상황

## 4. 테스트 피라미드

권장 비율:

- 단위 테스트: 가장 많음
- 통합 테스트: 중간
- E2E 테스트: 적지만 핵심만

이 프로젝트에서는 다음 정도를 목표로 한다.

- 단위 테스트 60%
- 통합 테스트 30%
- E2E 테스트 10%

정확한 수치보다 중요한 것은 범위다.

## 5. 프론트엔드 테스트 전략

Frontend: `Nuxt 3 + Vue 3`

권장 도구:

- Unit/Component: `Vitest`, `@vue/test-utils`
- E2E: `Playwright`

### 5.1 프론트엔드 단위/컴포넌트 테스트 대상

#### 기록 작성 화면

반드시 검증할 것:

- 제목이 비어 있어도 기록 작성 가능
- 본문 입력 시 로컬 상태가 즉시 반영됨
- autosave 상태 표시가 `저장 중 -> 저장됨`으로 전환됨
- autosave 실패 시 오류 메시지가 노출됨

#### 아카이브 화면

반드시 검증할 것:

- 기록 목록이 날짜순으로 렌더링됨
- 빈 상태 문구가 조건에 맞게 노출됨
- 검색어 입력 시 필터링 로직이 정상 동작함

#### 초안 화면

반드시 검증할 것:

- 초안 메타데이터가 정상 표시됨
- 기록 목록 순서가 상태에 맞게 렌더링됨
- reorder UI 조작 시 내부 상태 순서가 기대대로 변경됨

#### 인증 관련 상태

반드시 검증할 것:

- 비인증 상태에서 보호 라우트 접근 시 리다이렉트
- refresh 성공 시 세션 유지
- refresh 실패 시 로그인 화면 전환

### 5.2 프론트엔드 테스트 우선순위

가장 먼저 작성할 프론트 테스트:

1. 기록 작성 autosave 상태 테스트
2. 보호 라우트 접근 제어 테스트
3. 초안 순서 변경 상태 테스트

## 6. 백엔드 테스트 전략

Backend: `NestJS`

권장 도구:

- Unit/Integration: `Jest`
- API/HTTP 통합: `Supertest`

### 6.1 백엔드 단위 테스트 대상

#### Auth 서비스

반드시 검증할 것:

- 회원가입 시 비밀번호 해싱 처리
- 로그인 시 자격 증명 검증
- refresh token 유효성 검증
- 로그아웃 시 세션 무효화 처리

#### Entries 서비스

반드시 검증할 것:

- 기록 생성
- 기록 수정
- autosave 시 `lastSavedAt` 갱신
- 삭제 시 소유권 검증

#### Drafts 서비스

반드시 검증할 것:

- 초안 생성
- 기록 추가
- 기록 제거
- 순서 변경 시 position 재정렬
- 동일 초안 내 중복 기록 방지

### 6.2 백엔드 통합 테스트 대상

#### 인증 API

반드시 검증할 것:

- `POST /auth/signup`
- `POST /auth/login`
- `POST /auth/refresh`
- `POST /auth/logout`
- `GET /auth/me`

검증 포인트:

- 성공 응답 구조
- 잘못된 자격 증명
- 만료/위조 refresh token
- 로그아웃 후 refresh 거부

#### 기록 API

반드시 검증할 것:

- `POST /entries`
- `GET /entries`
- `GET /entries/:id`
- `PATCH /entries/:id`
- `DELETE /entries/:id`

검증 포인트:

- 사용자별 데이터 분리
- 존재하지 않는 ID 처리
- 타 사용자 리소스 접근 차단

#### 초안 API

반드시 검증할 것:

- `POST /drafts`
- `GET /drafts`
- `GET /drafts/:id`
- `PATCH /drafts/:id`
- `POST /drafts/:id/entries`
- `PATCH /drafts/:id/entries/reorder`
- `DELETE /drafts/:id/entries/:entryId`
- `GET /drafts/:id/preview`

검증 포인트:

- 초안 생성 시 entry ownership 검증
- reorder 시 position 충돌 방지
- draft preview 응답 구조 검증

## 7. E2E 테스트 전략

도구:

- `Playwright`

E2E는 많을 필요 없다.

하지만 아래 핵심 흐름은 반드시 보장해야 한다.

### 시나리오 1. 첫 기록 작성

1. 회원가입/로그인
2. 기록 작성 화면 진입
3. 제목 또는 본문 입력
4. autosave 상태 확인
5. 아카이브에서 기록 확인

### 시나리오 2. 초안 생성

1. 기존 기록 2~3개 준비
2. 초안 생성
3. 기록 추가
4. 순서 변경
5. 초안 목록/상세에서 반영 확인

### 시나리오 3. 미리보기 확인

1. 초안 상세 진입
2. 미리보기 이동
3. 제목/본문 흐름 확인
4. 수정 화면으로 복귀

### 시나리오 4. 인증 만료 복구

1. 보호 페이지 접속
2. access token 만료 시뮬레이션
3. refresh 시도
4. 세션 유지 또는 실패 처리 확인

### 현재 구현 상태

현재 저장소에서는 아래 핵심 검증이 이미 연결되어 있다.

- Jest / Supertest 기반 인증, 기록, 초안 API 검증
- Vitest 기반 프론트 composable / 상태 테스트
- Playwright 기반 core-loop smoke
- Playwright 기반 auth-expiry smoke

따라서 다음 단계의 테스트 확장은 "MVP를 증명하기 위한 첫 도입"이 아니라, 이미 닫힌 MVP를 유지하면서 Phase 2 회귀를 막는 방향으로 판단한다.

## 8. 커버리지 전략

커버리지는 숫자 자체보다 의미가 중요하다.

하지만 최소 기준은 설정한다.

초기 기준:

- Backend unit/integration line coverage: `70%+`
- Frontend unit/component line coverage: `60%+`
- 핵심 도메인 서비스(Auth, Entries, Drafts): `80%+`

주의:

- 단순 getter/setter를 커버리지 채우기 용도로 테스트하지 않는다
- 실패 시나리오가 포함되지 않은 높은 커버리지는 의미가 낮다

## 9. 우선 작성해야 할 실패 케이스

이 프로젝트에서는 정상 흐름보다 실패 흐름 테스트가 중요하다.

우선순위 높은 실패 케이스:

- autosave 실패
- refresh token 만료
- 타 사용자 리소스 접근
- 초안에 타 사용자 기록 추가 시도
- reorder payload 불일치
- 존재하지 않는 entry/draft 조회

## 10. TDD 우선 적용 대상

아래 영역은 가능하면 테스트를 먼저 작성한 뒤 구현한다.

### 인증

- refresh token 검증
- 로그아웃 후 세션 무효화
- 보호 리소스 접근 차단

### 기록

- autosave 시 상태 전이
- `lastSavedAt` 갱신 규칙
- 잘못된 저장 실패 처리

### 초안

- 동일 초안 내 중복 기록 방지
- reorder 시 순서 충돌 방지
- 타 사용자 기록 추가 차단

### 프론트 상태

- autosave 상태 표시 전이
- 인증 만료 후 refresh 성공/실패 분기

이 영역들은 구현 전에 실패 테스트를 먼저 작성하는 것이 회귀 방지에 특히 유리하다.

## 11. 테스트 데이터 전략

### 단위 테스트

- 최소 fixture
- 도메인 규칙 확인 중심

### 통합 테스트

- 테스트 전용 DB 상태 초기화
- 사용자 A / 사용자 B 분리 fixture
- entry / draft 관계 fixture

### E2E 테스트

- seed 기반 최소 사용자
- seed 기반 최소 기록
- 테스트 종료 후 격리된 환경 정리

## 12. CI와 테스트의 연결 원칙

테스트는 로컬에서만 돌면 의미가 약하다.

반드시 CI에 포함한다.

최소 CI 단계:

1. install
2. lint
3. typecheck
4. unit test
5. integration test
6. build

PR이 머지되기 전에 최소한 이 단계는 통과해야 한다.

## 13. 포트폴리오 관점에서 남겨야 할 증거

이 프로젝트는 이력서 보강용 프로젝트이기도 하다.

따라서 아래를 명확히 남긴다.

- 어떤 테스트 도구를 사용했는지
- 어떤 핵심 흐름을 자동 검증했는지
- 어떤 실패 케이스를 막았는지
- CI에서 어떤 단계가 자동화됐는지
- 테스트 도입으로 무엇이 더 안정적이 되었는지

예시 문장으로 재가공 가능한 형태:

- `Jest와 Supertest 기반으로 인증, 기록, 초안 API 통합 테스트를 작성해 소유권 누수와 reorder 무결성 회귀를 방지`
- `Vitest와 Playwright를 도입해 autosave, 초안 생성, 미리보기 핵심 사용자 흐름을 자동 검증`
- `GitHub Actions CI에 lint, typecheck, unit/integration test, build 단계를 구성해 PR 단계에서 품질 게이트를 자동화`
- `인증, autosave, draft reorder 같은 핵심 도메인 로직에 선택적 TDD를 적용해 회귀 리스크를 초기에 차단`

## 14. 구현 순서

테스트도 구현과 같이 단계적으로 도입한다.

### Phase 1

- Backend health/auth 기본 단위 테스트
- Frontend auth 가드 최소 테스트

### Phase 2

- Entries API 통합 테스트
- 기록 작성 autosave 컴포넌트 테스트

### Phase 3

- Drafts API 통합 테스트
- reorder 상태 테스트
- draft preview E2E

### Phase 4

- 전체 핵심 루프 E2E 보강
- CI 커버리지 리포트 연결

### 현재 기준

위 단계적 도입은 MVP 기간의 권장 순서였다. 현재는 core-loop smoke와 auth-expiry smoke까지 들어온 상태이므로, 다음 테스트 작업은 Phase 2 기능에 맞춘 새 리스크 식별과 최소 회귀 보호를 기본으로 한다.

## 15. 하지 말아야 할 것

- 처음부터 모든 화면을 E2E로 덮으려 하지 않는다
- 커버리지 숫자만 높이기 위한 의미 없는 테스트를 쓰지 않는다
- 리팩토링에 취약한 과도한 구현 세부사항 테스트를 남발하지 않는다
- UI snapshot만으로 안정성을 착각하지 않는다
- 시각 요소까지 억지로 TDD로 밀어붙이지 않는다
- TDD가 맞는 영역과 빠른 프로토타이핑이 맞는 영역을 구분하지 못한 채 전면 강제하지 않는다

## 16. 최종 기준

Book Maker의 테스트 전략은 아래를 만족해야 한다.

- 글 유실 리스크를 자동으로 검증한다
- 권한 누수를 자동으로 검증한다
- 초안 무결성을 자동으로 검증한다
- 인증 세션 회복을 자동으로 검증한다
- 핵심 사용자 흐름이 CI에서 지속적으로 검증된다
- 핵심 리스크 구간에는 선택적 TDD가 실제로 적용된다
