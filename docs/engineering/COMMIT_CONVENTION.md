# Book Maker Commit Convention

## 1. 목적

이 문서는 Book Maker 프로젝트의 커밋 메시지 형식과 커밋 분리 기준을 정의한다.

목표는 다음과 같다.

- 변경 목적을 커밋 단위에서 바로 읽을 수 있게 한다
- 작업 이력을 기능, 버그, 문서, 설정 단위로 추적 가능하게 만든다
- PR 리뷰와 회고 시 변경 맥락을 빠르게 이해할 수 있게 한다
- 이후 커밋 보조 스킬이 일관된 기준으로 메시지를 생성할 수 있게 한다

## 2. 기본 형식

커밋 메시지는 아래 형식을 따른다.

- `type: 한글 요약`

예:

- `feat: 기록 자동 저장 흐름 구현`
- `fix: 초안 미리보기 라우트 오류 수정`
- `docs: 인증 흐름 문서 보강`
- `chore: docker compose 로컬 개발 환경 추가`

## 3. 허용 타입

이 프로젝트에서 기본적으로 사용하는 타입은 아래와 같다.

- `feat`
- `fix`
- `docs`
- `chore`
- `refactor`
- `test`
- `ci`

필요 이상의 타입은 늘리지 않는다.

## 4. 타입 판단 기준

### feat

사용자 관점에서 새로운 기능이 추가되거나 의미 있는 기능 개선이 생긴 경우.

예:

- 기록 작성 기능 추가
- 초안 정렬 기능 구현
- 인증 흐름 추가

### fix

잘못된 동작, 회귀, 경계 조건 오류를 수정하는 경우.

예:

- 자동 저장 실패 시 상태 표시 오류 수정
- 초안 순서 저장 버그 수정
- 권한 검증 누락 수정

### docs

문서가 핵심 변경 대상인 경우.

예:

- 설계 문서 추가
- README 수정
- 테스트 전략 문서 보강

코드가 거의 없고 설명 자산이 중심일 때 사용한다.

### chore

기능 자체보다 환경, 설정, 부트스트랩, 템플릿, 인프라 준비가 중심인 경우.

예:

- 워크스페이스 초기화
- Docker Compose 추가
- GitHub 템플릿 추가
- `.env.example` 정리

### refactor

동작은 유지하면서 구조를 개선하는 경우.

예:

- 컴포넌트 분리
- 모듈 구조 재정리
- 중복 상태 로직 정리

사용자 기능 변화가 없어야 한다.

### test

테스트 코드가 변경의 중심인 경우.

예:

- e2e 테스트 추가
- 인증 회귀 테스트 보강
- 테스트 유틸 정리

### ci

CI/CD 파이프라인이나 자동화 워크플로가 변경의 중심인 경우.

예:

- GitHub Actions 워크플로 추가
- 테스트 단계 순서 조정
- 캐시 전략 수정

CI 변경이 단순 설정 부속인지, 워크플로 자체의 핵심 변경인지 애매하면:

- 워크플로 자체가 핵심이면 `ci`
- 일반 환경/설정 작업이면 `chore`

## 5. 메시지 작성 규칙

- 한국어로 작성한다
- 결과 중심으로 쓴다
- 과장된 표현을 쓰지 않는다
- 가능한 한 한 줄로 명확하게 끝낸다
- `추가`, `구현`, `수정`, `정리`, `분리`, `보강`, `동기화` 같은 명확한 동사를 사용한다

좋은 예:

- `feat: 아카이브 목록 조회 화면 구현`
- `fix: 만료 토큰 재시도 루프 오류 수정`
- `docs: 디자인 토큰 문서와 구현 기준 동기화`

좋지 않은 예:

- `feat: 이것저것 추가`
- `fix: 버그 수정`
- `chore: 작업`

## 6. 커밋 분리 기준

커밋은 논리적으로 읽히는 최소 단위로 나눈다.

좋은 분리 원칙:

- 설정과 기능 구현이 분리 가능하면 나눈다
- 문서와 코드가 독립적이면 나눈다
- 프론트와 백엔드가 하나의 목적이 아니라면 나눈다
- 리팩토링과 기능 추가가 섞이면 나눈다

같이 묶어도 되는 경우:

- 기능 구현 + 그 기능에 필요한 테스트
- 기능 구현 + 그 기능 설명을 위한 최소 문서 수정
- 설정 추가 + 그 설정을 사용하기 위한 필수 코드 수정

피해야 할 경우:

- 인증 작업 + 랜딩 디자인 수정 + CI 수정 + README 수정을 한 커밋에 섞기
- 같은 브랜치 안의 unrelated 변경을 한 메시지로 덮기

## 7. 타입 선택 우선순위

하나의 커밋에 여러 성격이 섞였을 때는 중심 변경을 기준으로 타입을 고른다.

예:

- 기능 구현이 중심이고 문서가 따라오면 `feat`
- 버그 수정이 중심이고 테스트가 따라오면 `fix`
- 테스트만 보강하면 `test`
- CI 워크플로 추가가 핵심이면 `ci`
- 설계 문서 정리가 핵심이면 `docs`

## 8. 브랜치와 PR 연계 기준

- 한 브랜치 안에도 여러 커밋이 있을 수 있다
- 하지만 각 커밋은 개별적으로 읽혔을 때도 의미가 있어야 한다
- PR 제목은 브랜치 전체 목적을 설명하고, 커밋 메시지는 그 내부 단계들을 설명한다

즉:

- 브랜치 = 작업 묶음
- 커밋 = 그 안의 논리적 단위

## 9. 하지 말아야 할 것

- 의미 없는 `wip`, `temp`, `misc` 커밋 남발
- 너무 큰 혼합 커밋
- 실제 변경보다 큰 메시지
- 테스트를 안 돌렸는데 돌린 것처럼 보이게 쓰기
- 문서 동기화가 필요한데 코드만 남기고 끝내기

## 10. 최종 기준

좋은 커밋은 다음을 만족해야 한다.

- 왜 바뀌었는지 메시지에서 바로 읽힌다
- 무엇이 바뀌었는지 diff와 자연스럽게 연결된다
- PR 리뷰 시 순서대로 읽어도 맥락이 끊기지 않는다
- 이후 자동화 스킬이 같은 기준으로 재현할 수 있다
